# W47 minimal local single-user Session contract — production issuer SEALED
Owner: W47, only `services/api/runtime/**`; supersedes no W24/W44/W25 contracts.

## Current implemented source
- **No extra Yance signup/login server**; no cloud, enterprise RBAC, SID/LUID broker or duplicate platform account manager. The local Session is an ephemeral, server-owned authorization for the current local application UI **only**, not proof of Facebook/WhatsApp/Telegram account/Peer or a grant to send.
- `createLocalSessionAuthority({approvePairing:null, ttlMs:300000})` is the default in the real `server.mjs`. There is **NO source-backed trusted native approval callback yet** in W54. Real `POST /api/v2/local-session/redeem` therefore always responds 503 `TRUSTED_NATIVE_PAIRING_NOT_AVAILABLE` for a well-formed request. Wrong Origin responds 403. Neither localhost nor browser-supplied Actor/Token/Origin, cookies, or WebView presence can activate approval. **Never substitute a synthetic test callback in deployed server**.
- `GET /api/v2/local-session/status`: public safe-state, default `{ok:true,paired:false,canSend:false,providerAuthorized:false,reason:"TRUSTED_NATIVE_PAIRING_NOT_AVAILABLE"}`. If an actually server-issued cookie exists in a future legitimately approved integration, returns paired:true, expiresAt, csrfToken (same-origin browser-only, never in HttpOnly session cookie), canSend:false/providerAuthorized:false. This is NOT a substitute for W24/W44 authorization.
- `POST /api/v2/local-session/redeem`: exact allowed browser Origin + JSON Content-Type + max 2048B body with **only** `{pairingCode:<32..256 chars>}`; one-time server-side verifier callback (not implemented by W54 yet) must consume its own genuinely native-approved, expiring pairing grant, with no client-supplied Principal. Only if callback returns true does W47 generate 32-byte random session ID/CSRF token and a five-minute in-memory expiry; it stores only SHA256(session-ID) map key, sends a `HttpOnly; SameSite=Strict; Path=/; Max-Age=300` cookie. Session is neither persisted nor accepted across API restart/instance.
- `POST /api/v2/local-session/logout`: exact Origin, valid server-owned cookie and matching session CSRF header `X-Yance-CSRF`, `Content-Type:application/json`, body `{}`; invalid/missing Session => 401; wrong/absent CSRF => 403; successful => server deletes session and expires cookie. Session authority also exposes server-only `revokeAll()` for future native logout/exit/revocation event; browser cannot call `revokeAll`. All sessions expire after five minutes, no implicit auto-extend, no token in URL, query or localStorage.
- Existing Host, loopback, exact Origin and Fetch Metadata/CORS blocking executes before session handler in `server.mjs`. A same-host same-SID malicious OS process remains a stated residual risk of the local-first threat model. Do not claim cookie over plaintext loopback provides strong protection against privileged malware; native signed app startup/installer and security Owner must review true trust channel.
